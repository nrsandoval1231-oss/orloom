## Objective and design

Replace the single syntax-only policy as the operator-selected final gate with **one finite, versioned `node-repo-suite-v1` check** for this repository family. Reuse the existing exact Git object extraction, private runner capability, durable artifact store, PostgreSQL attempt/certificate join, and `local-exact-commit` scope. A single check avoids adding a second certificate aggregation and policy-binding schema while the current slice stores one verification policy digest. Its trusted image runs fixed stages in order: dependency/lock admission, direct TypeScript typecheck, direct clean build, direct Node test discovery and execution, direct foundation validation, and an offline security check. The trusted image owns argv, stage order, timeouts, output limits, and pass criteria. It **never invokes `npm run`, `npx`, install lifecycle scripts, candidate shell scripts, or worker-supplied commands**. Candidate tests and `scripts/validate.mjs` remain untrusted code executed only inside `runsc`; their output is diagnostic data, never a verdict or policy update. A stage failure yields FAIL; timeout, missing stage, truncation, sandbox failure, or ambiguous process state yields UNKNOWN. PASS requires every stage to complete at the same extracted commit under the image/policy digest.

Build dependencies into the digest-pinned verifier image from an **operator-reviewed, exact `package-lock.json` digest** and a trusted build context. Record the lock digest, pinned Node/TypeScript/tool versions, base image digest, package integrity results, and final image digest in the policy/evidence. At run time, reject candidate `package.json` or lock bytes that do not match that admitted dependency set. Do not fetch packages or reuse a mutable host cache during verification. Mount or link the image's read-only dependency tree for Node resolution; reject candidate `node_modules`, `.npmrc`, and other paths that could override it. The container has no network or credentials. A lock change requires a new reviewed image and policy digest; it cannot silently inherit an old certificate. The security stage should make a narrow, testable claim: offline checked dependency integrity/allowlist and repository policy (forbidden workflow/credential material), plus vulnerability findings only if a versioned, pinned advisory snapshot is actually bundled. Do not call the result a current vulnerability audit without such a snapshot.

Extend the trusted launcher for this one policy with a clean writable build area and measured resources; do not change the frozen syntax policy's meaning. Keep source input bounded and rehash it inside the sandbox. Preserve runsc, no network, nonroot, read-only root, dropped capabilities, no privileges, fixed host slot, durable interruption quarantine, and no host source mount. The existing 256 MiB memory, 32 MiB `/work`, 0.5 CPU, and 60-second limits are unsuitable as assumed build-suite capacity. Select increased **one-check** caps only after measured runs on the cached 2 CPU/4 GB host leave room for PostgreSQL/control-plane and the protected container. Version the cap, timeout, image, dependency lock, stage manifest, and offline security dataset in the policy digest. An over-budget run is UNKNOWN, not a relaxed retry.

## Packet boundary

- **Allowed source:** `packages/verification/src/{policy,runner,runsc-launcher,repository}.ts`, `apps/verifier/src/index.ts` only if dispatch must select the new policy, `apps/control-plane/src/main.ts` and `packages/config/src/config.ts` only for operator selection of the new finite check, `infra/verifier-isolation/{Dockerfile,run-check.js,launch-verifier.sh,README.md}` and dedicated `tests/verification-*.test.ts` for the suite. Add a small trusted offline policy/data file under `infra/verifier-isolation/` only if its digest is included in the image/policy. No schema migration or new service is expected. Controller owns packet/evidence bookkeeping.
- **Exclusions:** PR #2 branch/broker, `outputs/orloom`, `packages/learning`, C1a recovery/lesson promotion, Governor certificate rules, SQL certificate semantics, GitHub App/R2/deployment/remote state, provider spending, and product PR merge. Any required change outside allowed files is a controller replan, not builder scope expansion.
- **Deterministic acceptance:** tests prove policy cannot be selected or altered through mission/worker text; lock mismatch and candidate `node_modules`/config overrides fail closed; direct trusted argv is used; each stage failure, timeout, truncation, and missing result prevents PASS; changed candidate/ref/policy/image invalidates certificate read. Reproduce build, typecheck, repository tests, validation, diff check, and existing C3 negative gates on the frozen exact commit.
- **Runtime acceptance:** on the existing DO host, preload the exact reviewed dependency image; run the full suite against one real clean extracted commit through `runsc` and the private route to actual PostgreSQL; retain per-stage bounded logs, hashes, resource/elapsed measurements, and one certificate. Prove one genuine failing candidate, one lock mismatch, timeout/interrupt UNKNOWN, and stale-head denial. Restart/reconnect and read the persisted artifacts/certificate. If the host cannot fit the measured cap, report C3 suite as capacity-blocked; do not certify from a host or mocked fixture alone.

## Learning and remaining gates

The existing syntax certificate cannot validate C1b lesson claims: syntax passing does not independently demonstrate a failed check becoming a passing check or an effective strategy. Even a full-suite certificate establishes only the exact candidate's check result. C1b must separately join independent failed and passed attempts to C1a progress event IDs, preserve comparable cohort/policy and ordering, challenge attribution across repeated episodes, show a later authorized strategy change, and support withdrawal after contrary evidence. Promotion stays closed until that behavioral verifier passes. Remote GitHub freshness, GitHub Checks, R2 retention, and live provider execution remain operational or later implementation gates; they are not implied by a local suite certificate.
