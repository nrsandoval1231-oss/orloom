# ORL-B-SANDBOX-PROOF preparation

This packet prepares a bounded runtime proof for the frozen worker sandbox entrypoint. It does not run a provider, broker, GitHub checkout, or untrusted job. A successful run proves the stdio protocol fixture and selected Docker restrictions only; it does not establish six-lane capacity, build reliability, provider access, or production readiness.

## Freeze gate

Do not copy, build, or run these scripts against the worker candidate until the controller supplies frozen SHA-256 values for `apps/worker/Dockerfile.sandbox`, `apps/worker/src/sandbox-entry.ts`, and `dist/apps/worker/src/sandbox-entry.js`, plus the exact source-manifest SHA. `prepare_context.py` checks all three file hashes and stages exactly the Dockerfile and compiled entrypoint into the build context. It writes `candidate-context-proof.json` outside that context and refuses a nonempty context or an existing identity file. The Node base is the parent-verified linux/amd64 manifest `node:24-bookworm-slim@sha256:51b1100cc2a83d370c6a60952e3f2989c8a43159d0e38586e090f3b3326efefd`.

## Disposable scope

The build creates `orloom-worker-sandbox-proof:<first-12-source-manifest-sha>` only. The runner creates at most two concurrent containers with names matching `orloom-worker-proof-<unix-seconds>-<pid>-<8-hex>-a|b`, label `org.orloom.worker-runtime-proof=true`, and source identity labels. Containers use `runsc`, `network=none`, read-only rootfs, uid/gid 65532, no capabilities, no-new-privileges, pids 64, memory/swap 256 MiB, CPU 0.5, and only private tmpfs mounts `/tmp` and `/work`. There are no binds, volumes, host sockets in the container, provider values, or credentials. Docker CLI calls use `/usr/bin/docker`, the explicit local socket, and an initially empty mode-0700 temporary config with a sanitized environment. The runner resolves the proof image tag to its immutable image ID, creates both containers by ID, records their IDs, and verifies those exact IDs and every provenance label before cleanup. `--rm` and the runner's `finally` block reap the exact test IDs; `cleanup_owned.sh` is an explicit recovery path that requires the exact IDs, names, source hashes, and base-image provenance before removal. No volume or host directory is created. Keep the built local image as evidence until the controller decides whether to remove it; image cleanup is not automated here.

1. On the workstation, invoke `prepare_context.py` with `--repo-root <exact outputs/orloom checkout>`, `--context <checkout>/work/worker-runtime-proof/candidate-context`, and all four frozen hashes. 2. On the DO host, use the exact temporary context path and source-manifest SHA: `bash build_candidate.sh <context-path> <source-manifest-sha256>`. The script checks the exact file set and content hashes before building with `--network=none` and `--pull=false`.
3. Run `python3 run_proof.py --image orloom-worker-sandbox-proof:<first-12-source-manifest-sha> --source-manifest-sha256 <sha> --dockerfile-sha256 <sha> --sandbox-source-sha256 <sha> --compiled-entry-sha256 <sha>`. Save only the single sanitized JSON evidence record. It contains test names, hashes, exact image/container IDs, protected `codex-universal` ID/start/restart/status fields before and after, inspect policy fields and timings; it does not print host environment values, tokens, or fixture secrets. 4. A failure after creating containers must be classified from exact IDs and all source labels before retry. The script checks that both exact IDs are absent before PASS. If the controller must manually recover containers, invoke `bash cleanup_owned.sh <source-sha> <dockerfile-sha> <sandbox-source-sha> <compiled-entry-sha> <exact-name-a>=<exact-id-a> <exact-name-b>=<exact-id-b>` after inspecting each exact ID. Never use broad name filters or remove unknown containers.
5. Remove the exact temporary staging directory only after checking its resolved path is the dedicated proof staging location. Keep the source-bound image/evidence until review decides retention.

## Test sequence

Both containers are created and started before fixture traffic; Docker inspect checks both at once. Each lane initializes two hashed files, reads one, rejects `../../etc/passwd`, replaces a unique marker, runs a fixed trusted Node check, denies a write into the image rootfs, and snapshots/verifies changed bytes and SHA-256. It then verifies symlink reads are rejected, output from a 70,000-byte check stays within 64,000 bytes, and a one-second check timeout terminates within four seconds. Closing each protocol removes `/work/tree`; Docker `--rm` then removes the exact container. The test does not instantiate `apps/worker/src/docker-runtime.ts` or exercise its checkout/Git candidate bridge; it exercises the compiled `sandbox-entry.js` process boundary directly.
