# Trusted local verification (ORL-C3)

The control plane starts this lane only when the complete trusted runner configuration is present and a PostgreSQL mission store is active. Otherwise certification stays disabled. This produces Orloom-local evidence for one exact commit; it does not publish GitHub Checks, prove remote freshness, or verify integration.

## Controller-owned candidate admission source

An optional `AdmittingVerificationRunner` now bridges persisted worker candidate artifacts to the existing verifier. It is a controller-composed source API, not a new HTTP upload/certification route or environment-variable activation switch. Normal startup does not instantiate it; the operator-configured local-repository runner above remains the executable path. Worker startup remains disabled.

The Governor derives the final-candidate binding from the approved mission, persisted slice, lease epoch, scopes, plan/policy digests and evidence references. Admission requires exactly one content-addressed candidate bundle and evidence index, verifies both SHA-256 bindings, and checks the index identity, exact approved-base prerequisite, single direct-child candidate commit and in-scope diff. It imports into a private bare object store without executing or checking out target code, extracts bounded regular files, and gives the verifier an immutable source manifest and candidate-local observed head. It never moves the operator's approved base ref. Per-candidate facades share the verifier's existing concurrency limit and cannot rebind prepared attempts.

This source path requires Linux `/usr/bin/git` and `/usr/bin/prlimit`, an existing owner-only real admission directory, an operator-owned repository map and an injected bounded artifact reader. Fixed-argument subprocesses disable hooks/config/network protocols and enforce child resource limits, output caps and deadlines. The complete admission deadline is 90 seconds; each Git subprocess is capped at ten seconds. Artifact limits are 20,000,000 bundle bytes and 256,000 index bytes, with at most 12,000 untrusted pack objects. There is one active admission per controller process and at most six cancellable waiters. The dedicated admission root must be used exclusively by one controller process; this source does not provide a cross-process lock. A 16-entry retention cap includes stale staging entries and refuses new imports at capacity. There is no automatic eviction: operator retention/reconciliation remains required.

Published admission receipts and extracted manifests are re-read and checked on reuse, including strict object integrity checks. Malformed or unbound candidates cannot create a trusted pass. Capacity pressure, caller cancellation and transient artifact transport failures before dispatch remain eligible for retry without a permanent dispatch-failure row or a durable verification attempt; invalid candidate preparation is retained conservatively as unavailable/UNKNOWN. No admission failure grants a certificate, integration, budget refund or capacity release. Recovery checkpoint admission is explicitly refused by this optional runner and remains a separate implementation gate.

The [foundation validation record](validation/2026-10-14-foundation.md) defines acceptance for this source addition. Local Git and injected artifact/launcher tests do not establish live R2 transport, a Docker/runsc check, live PostgreSQL, remote publication or a running worker. The disposable PGlite certificate-readback test uses a synthetic controlled launcher response only; it is not a genuine runtime certificate. Once a verifier attempt exists, its conservative UNKNOWN/expiry and no-redispatch semantics are unchanged.

## Operator setup

Set these values in the protected control-plane environment. `.env.example` contains blank names only.

- `ORLOOM_VERIFIER_IMAGE`: immutable `repository/name@sha256:<64 lowercase hex>` or an inspected local Docker image ID `sha256:<64 lowercase hex>`. Tags are rejected. The launcher inspects the local image immediately before creating a sandbox and confirms the configured digest.
- `ORLOOM_VERIFIER_ID`: stable operator-assigned verifier identity.
- `ORLOOM_VERIFIER_ARTIFACT_ROOT`: persistent directory outside the source worktree and temporary directories. The artifact store uses content-addressed `sha256/<digest>` keys and refuses unsafe paths.
- `ORLOOM_VERIFIER_REPOSITORIES`: JSON object mapping canonical `owner/repo` to `{ "objectStore": "/absolute/path/to/repo.git", "approvedRef": "refs/heads/main" }`. The object store and ref are operator-controlled; mission text cannot select paths or commands.
- `ORLOOM_VERIFIER_LAUNCHER`: optional absolute path to the fixed host launcher. The default is `/opt/orloom/infra/verifier-isolation/launch-verifier.sh`.
- `ORLOOM_TRUSTED_CHECK_POLICY_JSON`: must include the selected finite check ID to enable verification. `ORLOOM_VERIFIER_CHECK_ID` selects a trusted catalog entry and defaults to `node-validate-syntax`; it cannot provide commands.

The launcher requires the protected Linux host service to run as root, Docker at `/usr/bin/docker`, `flock`, and the `runsc` runtime. Preload and inspect the verifier image on that host. The launcher has no network, mounts no host source tree or credentials, runs as UID/GID 65532 with a read-only root, dropped capabilities, no-new-privileges, 0.5 CPU, 256 MiB memory, 64 PIDs, and bounded tmpfs. It serializes all processes with a protected host-wide lock in `/run/orloom-verifier-lock` and stores durable intent/container identity under `/var/lib/orloom/verifier/state`. The shared `/var/lib/orloom` parent must already be root-owned and not group/world writable; the launcher validates but never changes its permissions. It creates a dedicated mode-0700 verifier directory for slot state. After restart it only removes a previously recorded exact container after the ID, ORL-C3 label, invocation name, and image all match. Unknown creation effects and identity/daemon inspection failures leave the slot quarantined for operator reconciliation; no unrelated container is enumerated or removed. Keep `/var/lib/orloom` persistent. Artifacts and uncertain slot state must remain durable across process restarts.

## Execution and evidence

The catalog retains `node-validate-syntax` with its original `node --check scripts/validate.mjs` meaning and 60-second deadline, and adds `node-repo-suite-v1`. The suite admits the exact reviewed package/lock pair and runs fixed typecheck, clean build, nonempty test discovery/execution, and foundation validation stages under a 360-second total image deadline. Its finite trial timer chain is bound by the selected suite policy digest: 360 seconds for the image suite, 390 seconds plus the existing two-second kill grace for Docker attach, 405 seconds for the host launcher, and 420 seconds for the trusted attempt request. The existing 120-second post-deadline reporting grace and ten-minute request-contract maximum are unchanged; attempt plus settlement totals 540 seconds. These are conservative trial allocations following an observed incomplete run prefix; they are not measured proof that the full suite fits. Timeouts and ambiguous cleanup remain UNKNOWN. Its offline path policy rejects workflow files, `.env` values other than `.env.example`, private-key formats, `secrets/`, `credentials/`, and `state/` paths, dependency/config override paths, and source files under `dist/`. It does not scan file contents for credentials and makes no vulnerability-audit claim. Source permissions only discourage accidental writes: after execution the trusted runner compares every manifested input byte-for-byte with the original manifest. The suite trial profile is one concurrent check, 1 CPU, 2 GiB memory with swap held to the same 2 GiB cap, 128 PIDs, 512 MiB `/work`, 16 MiB `/tmp`, up to 16 MiB input and 64 KiB per log. This is not a proven sufficient peak; host capacity must be measured before a runtime attempt. The syntax-only profile remains at 256 MiB memory and swap. Image build, lock update, check, or limit changes invalidate the policy digest. The repository extractor verifies the candidate commit and base ancestry against the approved local ref, rejects unsafe tree entries, and stages regular files only.

The control plane polls PostgreSQL every five seconds and dispatches at most one awaiting check at a time. A unique mission/slice/epoch/check attempt key prevents concurrent or restart-driven redispatch. The host launcher inspects the created Docker container and starts it only when memory, equal memory-swap cap, CPU, PIDs, network, read-only root, user, runtime, capabilities, security option, and tmpfs settings match the selected fixed profile. The verifier capability is kept in the control-plane process; there is no worker or owner receipt-submission route. It expires 120 seconds after the check deadline. Late PASS/FAIL is rejected; a late UNKNOWN can be recorded during grace. The expiry reconciler records UNKNOWN after grace, including attempts interrupted by restart. Normal SIGTERM/SIGINT shutdown stops polling and awaits the active reconcile/verification before closing PostgreSQL. Failures to read the candidate or authoritative ref are retained as UNKNOWN dispatch events without manufacturing a request or artifact.

PASS creates one immutable certificate and one `check.certified` event in a PostgreSQL transaction after artifact read-back, receipt digest, approved plan, candidate SHA, lease epoch, selected policy, and current local head all match. The owner view checks those bindings again and hides a certificate if the local ref has moved. Certification never changes slice status, integrates code, releases budgets, or promotes lessons.

The repository-suite image emits bounded `orloom.suite-diagnostics.v4` stage and per-file start/end frames with fixed stage names, sorted test basenames, elapsed milliseconds through the 360-second suite ceiling, and a finite outcome. Every discovered test file executes serially in its own Node invocation. These frames are advisory telemetry only: repository code shares the sandbox and can forge diagnostic-looking data, so frames never establish PASS or FAIL. On ambiguous launcher output the host retains only complete, schema-valid, ordered frames (at most 64 frames and 16 KiB; basename limit 128 bytes; telemetry ordinal limit 64) and discards all other text. Telemetry limits never omit tests or stop execution. Exit status remains UNKNOWN with no certificate. A missing or partial final result marker, timeout, signal, or truncation cannot be resolved from a stage frame.

Source `4d1dd56` passed 75 local tests and independent source review. Its real full-suite attempt remains UNKNOWN with zero certificates after sandbox OOM during `jobs.test.js`; five preceding test files completed. The exact container measurements and cleanup evidence are retained in [the diagnostic record](evidence/c3-suite-memory/EVIDENCE.md). The full repository suite has not yet earned cloud certification.

`tests/verification-certification.test.ts` uses PostgreSQL-compatible PGlite and explicitly injected fixture runner boundaries for deterministic behavior tests. It is not a real runsc host proof. A genuine runner-to-PostgreSQL proof still requires the configured protected host, pinned preloaded image, operator repository map, and durable artifact path.


## Governed Orloom execution input

The operator may set `executionInputProfile: "orloom-execution-v1"` on the Orloom entry in `ORLOOM_VERIFIER_REPOSITORIES`. The default is unchanged full-tree extraction. Unknown profile values fail closed. The profile is trusted controller code, never candidate-controlled JSON or ignore rules; changing it requires controller code review and deployment authorization.

This profile selects all files under apps, packages, tests, scripts, db, deploy and infra, plus current docs outside historical evidence/validation, the slice1c verification helper, README, package/lock/TypeScript configuration and the four root dot configuration files. No source extension filter is used: newly added source files under these roots are included automatically. Unknown roots are refused and must be explicitly classified. Historical `.agent/`, `docs/evidence/`, `docs/validation/` (except that imported helper), `work/`, `prototypes/`, `forge/`, and the two root PR23 receipt/source checksum files are execution-excluded. These are records and historical demonstrations, not active application build inputs. Checks of archived demonstrations remain separate work; this profile does not certify them.

The full tree is still inspected for unsafe paths, collisions, symlinks/gitlinks, count and per-file size bounds. Parent, scope, bundle/index digest, pack, fsck, private-store, queue, deadline, retention and resource limits remain unchanged. Excluded changes still undergo scope checks. No evidence files are deleted, moved or rewritten. The complete candidate Git tree and historical objects remain in the private admitted bare repository, including excluded bytes. Restore any record by its full candidate SHA and path using Git object reads. The input manifest binds the candidate SHA, full tree SHA, fixed profile version, exclusion count/bytes, and selected content hashes. Recompute classification from that tree and the reviewed profile to reproduce selection; cached admission rechecks the same binding and refuses profile drift.

The 16,777,216-byte limit continues to cover selected source plus manifest. Selecting a profile is not permission to run a provider, activate production, publish externally, or certify runsc. Use `node scripts/prove-execution-admission.mjs SOURCE BASE_SHA CANDIDATE_SHA OUTPUT` after a clean build for a credential-free, bounded real-Git admission proof. It requires a real direct child of the approved base and confirms complete tree preservation; it does not dispatch a sandbox or complete an autonomous engineering task.
