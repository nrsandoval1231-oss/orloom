# Judgment, active recovery, and operational lessons

This C1 slice adds durable, lease-fenced trusted-check progress and finite recovery decisions. A worker posts `orloom.progress.v1` to `POST /api/worker/missions/:missionId/slices/:sliceId/progress`; its mission, slice, epoch, plan digest, trusted check policy digest, recovery policy digest, and capability must match the active lease. `GET /api/worker/missions/:missionId/slices/:sliceId/recovery-policy` returns the operator-approved strategy map for that lease. Progress records contain fixed IDs, bounded counters, and SHA-256 evidence references, not prompts, stdout, source, or model reasoning.

The SQL store first persists an immutable snapshot and a `prepared` progress row. It releases its transaction before invoking the optional judgment adapter, then reopens a transaction and compares the active lease fence, snapshot revision, plan/check/recovery policy digests, and promoted-lesson binding. Only the Governor commits a finite action. A dispatched judgment with uncertain results, invalid output, an expired lease, or a changed fence becomes `UNKNOWN` and leaves the slice quarantined. Identical committed progress replays return the prior receipt only while the caller still proves the active lease; conflicting content and unresolved retries fail closed.

`createControlPlane(config, jobs, store, judgmentAdapter?)` is the explicit injection seam. Without an injected adapter, decisions use deterministic selection among the snapshot's approved strategy IDs. The Jev adapter uses the installed `@typesafe-ai/sdk` 0.6.0 `TypeSafeClient.systemOne` choice API, exact allowlisted model IDs, fixed HTTPS origin, bounded request/response bytes and deadline, and disabled retries. It cannot issue commands or change a plan. Production does not instantiate it by default. No credential, provider request, spend, or live Jev acceptance is claimed for this packet; an operator must provide exact model, credential, and a separately approved spend policy before configuring a live adapter.

An operational lesson is a versioned candidate based on two separate same-repository/scope-cohort episodes, each containing a trusted-check failure followed by a pass under a different approved strategy. Candidates state the fixed metric (`trusted_check_pass_rate`), direction, comparable baseline/outcome counts, policy version/digest, rule, and four immutable progress event IDs. Candidates and their provenance are durable, but promotion is deliberately disabled: authenticated `POST /api/lessons/:lessonId/promote` returns HTTP 503 with `Independent lesson verification is unavailable; candidate remains unpromoted`. There is no independent evidence verifier in this checkpoint, so a typed owner challenge cannot certify a worker-reported result. C1a never consumes lessons in later decisions or records a promotion/withdrawal. Promotion, downstream policy use, and contradiction handling remain open for a trusted-verifier packet.

The controlled checks and Jev transport tests are fixtures. Their results do not establish product-build success, quality improvement, performance gain, provider capability, or live cost. The full recovery system remains open: this packet does not yet model near-identical patch fingerprints, provider/tool-call history and nonprogress attribution, regressing verification, blocked dependency recovery, or integration-conflict signals. Independent code verification remains unavailable and the integration gate stays closed. PostgreSQL deployment/runtime claims require the separate real-PostgreSQL proof bound to the frozen candidate.
